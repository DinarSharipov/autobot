# Юзкейсы баланса и тестовых покупок

Дата: 2026-11-10. Статус всех сценариев: **Не проверено**.
Документ задаёт ожидаемое поведение; наличие сценария не подтверждает его реализацию или прохождение.
Контракт и ограничения: [TEST_CHECKOUT_CLIENT.md](TEST_CHECKOUT_CLIENT.md).

## Подготовка и фиксация результата

Использовать изолированные бот, backend и базу, тестовый магазин YooKassa и аккаунт из backend allowlist.
Для позитивных покупок: `BOT_TEST_CHECKOUT_ENABLED=true`, `NODE_ENV=test` либо `development`,
на backend настроены test checkout, webhook и return URL. Реальные деньги не используются.
Для отрицательных проверок нужны второй пользователь и возможность управлять доступностью
тестового backend/provider и доставкой тестовых событий. Ключи в отчёт не включать.

Перед каждым кейсом записать версии бота/backend, язык Telegram и исходные балансы/резервы/долг.
После выполнения сохранить ID заказа, несекретный результат API, изменения ledger и наблюдение UI.
Для повторов сравнивать ID заказа, provider payment ID, число PURCHASE-записей и итоговый баланс.
Результаты заносить в [E2E_TEST_STATUS.md](E2E_TEST_STATUS.md): **Готово**, **Не проверено** или
**Ошибка**. При ошибке приложить шаги воспроизведения и issue/commit. Статические проверки
и ответы HTTP 200 не заменяют сквозную приёмку.

## UC-PURCHASE-01 — Посмотреть баланс и операции

**Предусловия:** пользователь авторизован в Telegram, backend доступен.

1. Открыть `/balance`, затем историю операций и вернуться.
2. Сверить TEXT/IMAGE: доступно, в резерве, задолженность; сравнить последние 10 операций с API.
3. Обновить баланс после контролируемого изменения backend; повторить с пустой историей.

**Ожидается:** значения принадлежат текущему пользователю, отсутствующий кошелёк не отображается
как нулевой. История показывает вид операции, величину, дату и тип кредита. Повторное открытие
не дублирует серверный onboarding gift. Для частичного ответа кошельков использовать
контролируемый тестовый ответ, не удалять реальные записи.

## UC-PURCHASE-02 — Выбрать пакет и проверить цену заказа

**Предусловия:** тестовые покупки включены, каталог содержит TEXT и IMAGE.

1. Открыть каталог, просмотреть страницы по пять пакетов, выбрать пакет.
2. Сравнить количество, валюту и цену заказа с backend snapshot.
3. До подтверждения проверить отсутствие созданного provider payment и PURCHASE-записи.

**Ожидается:** создан один заказ; выбор пакета не начинает оплату и не выдаёт кредиты.
Окончательная цена показана до отдельного подтверждения. Повторить для обоих типов пакетов.

## UC-PURCHASE-03 — Успешно оплатить тестовый заказ

**Предусловия:** создан неоплаченный заказ, известны исходный баланс и ledger.

1. Подтвердить показанную цену и создать тестовый платёж.
2. Открыть HTTPS-ссылку, выполнить успешную оплату тестовым способом магазина.
3. Вернуться в бот и нажать «Проверить оплату»; открыть карточку и баланс.

**Ожидается:** backend подтверждает `paymentStatus=SUCCEEDED` и `fulfillmentStatus=FULFILLED`.
Есть ровно один PURCHASE grant на количество из заказа; второй тип кредита не пополнен.
При наличии долга учитывать серверное погашение долга, а не ожидать увеличения available на всю сумму.
Цена и количество берутся из snapshot заказа. Повторить для TEXT и IMAGE.

## UC-PURCHASE-04 — Вернуться без оплаты или отменить платёж

1. Создать тестовый платёж и вернуться в Telegram, не оплачивая.
2. Нажать проверку; затем отдельным заказом воспроизвести отмену тестовым провайдером.

**Ожидается:** возврат по ссылке не выдаёт кредиты; pending остаётся pending.
При подтверждённой отмене показано терминальное состояние, PURCHASE grant отсутствует.
Отсутствующий `expiresAt` не превращается в выдуманный срок; EXPIRED проверяется только
если backend вернул его явно.

## UC-PURCHASE-05 — Повторить клик и восстановиться после сетевой ошибки

1. Дважды нажать выбор одного пакета; воспроизвести потерю ответа после создания заказа.
2. Повторить тот же запрос кнопкой на странице ошибки.
3. Потерять ответ после создания платежа, восстановить ссылку для того же заказа.
4. Повторить исходную кнопку создания уже оплаченного/отменённого заказа: бот должен
   перечитать текущее состояние через GET, а не показать первоначальный idempotency snapshot.

**Ожидается:** повтор выбора использует тот же Idempotency-Key и возвращает тот же заказ.
Платёжная попытка и provider payment ID не меняются; списаний и зачислений нет в дубле.
Бот не запускает новую покупку автоматически. Повторить при восстановлении не редактируемой
страницы сообщения. Отдельное осознанное открытие каталога и выбор создаёт новую покупку.

## UC-PURCHASE-06 — Продолжить покупку после перезапуска

1. Создать заказ/платёж и перезапустить только тестового бота.
2. Через «Баланс → История заказов» открыть тот же заказ и продолжить покупку.
3. После успешной оплаты снова перезапустить бота и проверить заказ.

**Ожидается:** заказ и ссылка восстанавливаются из backend, локальный черновик не нужен.
Для заказа с созданной платёжной попыткой отдельная кнопка проверки доступна и после FULFILLED;
обычное обновление карточки при этом остаётся GET без обращения к провайдеру.
Перезапуск не создаёт второй заказ, платёж или grant. История ограничена последними 100 заказами;
этот кейс использует заказ внутри данного окна.

## UC-PURCHASE-07 — Дождаться подтверждения и зачисления

1. В тестовом контуре задержать provider-проверку/webhook и выполнить проверку оплаты.
2. Воспроизвести ответ `SUCCEEDED/PENDING`, затем завершить серверное fulfillment/reconciliation.
3. Повторить проверку после `FULFILLED`.

**Ожидается:** HTTP 200 с pending не трактуется как успешная покупка. Подтверждённая оплата
с незавершённым зачислением показана отдельно. Последующая проверка отражает новое состояние;
выполненный grant не повторяется. Для недостижимого вручную промежуточного состояния использовать
изолированный fault injection; не редактировать финансовые записи напрямую.

## UC-PURCHASE-08 — Каталог изменился во время покупки

1. Показать пакет, затем изменить его цену/версию/количество или отключить на backend.
2. Нажать старую кнопку выбора.
3. Отдельно изменить каталог между повторным чтением и созданием заказа, затем после создания.

**Ожидается:** устаревшая кнопка требует обновить каталог. Если изменение произошло в гонке
создания заказа, фактическая новая цена показана до запуска платежа. Уже созданный заказ сохраняет
snapshot. При неизвестном результате create и изменённом каталоге пользователь сначала проверяет
историю; клиент не пытается обойти неопределённость новой автоматической покупкой.

## UC-PURCHASE-09 — Ограничения доступа и отключение checkout

1. С выключенным флагом открыть каталог и отправить старые checkout callbacks.
2. Проверить отказ запуска с `NODE_ENV=production` и включённым тестовым флагом.
3. В изолированном контуре проверить пользователя вне allowlist и выключенный backend checkout.
4. Вторым пользователем попытаться открыть, оплатить и проверить чужой order ID.

**Ожидается:** default UI доступен для чтения, старые кнопки не создают заказ/платёж.
Production не запускается с тестовым checkout. Backend-ограничения отображаются понятно,
чужой заказ не раскрывается и не меняется. Серверные секреты и provider payload не выводятся.

## UC-PURCHASE-10 — Ошибка провайдера и ручная сверка

1. Воспроизвести timeout/недоступность провайдера, неверный ответ и ошибку проверки платежа.
2. Воспроизвести `PAYMENT_RECONCILIATION_REQUIRED` для неопределённой старой попытки.
3. Открыть историю и повторить запрос того же заказа, где это допускает backend.
4. Отдельно проверить обрыв тела HTTP-ответа после заголовков, некорректный JSON и
   JSON с неправильной billing-схемой. Повтор допустим только для GET и запросов со стабильным
   Idempotency-Key; payment create/check POST автоматически не повторяются.

**Ожидается:** нет ложного сообщения о зачислении; нет автоматического нового заказа или
нового provider key. При необходимости ручной сверки показано обращение в поддержку;
клиент не обходит серверный запрет повторным созданием платежа.

## UC-PURCHASE-11 — Дубли и порядок событий оплаты

1. На тестовом backend повторить webhook успешного платежа и параллельно выполнить ручную проверку.
2. Доставить старое pending/canceled событие после успешного подтверждения.
3. Выполнить backend reconciliation и снова открыть заказ/баланс.

**Ожидается:** одно зачисление, fulfilled не откатывается старым событием, UI соответствует
серверу. Это совместная приёмка backend и бота; клиент не имитирует webhook от имени пользователя.

## UC-PURCHASE-12 — Возврат и задолженность

1. Для подтверждённого тестового заказа выполнить серверный сценарий частичного/полного возврата.
2. Сравнить refundStatus, возвращённую сумму и отозванные кредиты в карточке с backend.
3. Повторить со spent/reserved credits и открыть баланс с долгом.

**Ожидается:** бот только показывает подтверждённое состояние. История ledger сохраняется;
Checkout также сообщает о полном/частичном возврате, сумме и отозванных кредитах,
а не только о первоначальном зачислении. Проверить и старую checkout-кнопку после возврата.
баланс, debt и округление отзыва определяет backend. Повторное чтение не выполняет возврат.

## UC-PURCHASE-13 — Навигация, языки и объём данных

1. Повторить основной путь на RU/EN; проверить страницы каталога/заказов, пустые списки и последние записи.
2. Перейти в другой раздел во время ввода; нажать кнопку старого сообщения.
3. Проверить сообщение с HTTPS-ссылкой, клавиатуру, возврат в баланс и обновление карточки.

**Ожидается:** полный перевод, корректные деньги/даты, page callbacks не воздействуют на другой
заказ; главная клавиатура сохранена. Invalid/non-HTTPS URL не предлагается для оплаты.
Обычное обновление карточки выполняет только GET; проверка оплаты — отдельное действие.
При синтаксически некорректной URL карточка остаётся доступной без ссылки; показано пояснение,
сохранены восстановление ссылки и проверка той же оплаты. Повторить с HTTP и HTTPS с credentials.

## UC-PURCHASE-14 — Пополнение и явное продолжение генерации

**Предусловия:** отдельный prepaid-стенд, операция TEXT или IMAGE в BLOCKED_FUNDS.

1. Пополнить нужный тип кредита тестовой покупкой; проверить баланс и blocked occurrence.
2. Открыть «Баланс → Публикации и возобновление», найти occurrence, обновить состояние.
3. Явно возобновить TEXT или существующую IMAGE-операцию; повторить тот же запрос при timeout.
4. Проверить новый funds block после неудачного пополнения, повторное открытие после рестарта
   и недоступность resume для legacy/чужой/отменённой/уже выполняющейся операции.
5. Повторить с заменой изображения: старая картинка уже выбрана, а новая IMAGE-операция
   BLOCKED_FUNDS; кнопка resume должна быть доступна даже при fundingStatus=READY у публикации.

**Ожидается:** пополнение само не запускает генерацию и не покупает другой тип кредита.
Resume сохраняет occurrence и согласованное платное намерение, не дублирует debit.
UI resume реализован; постановка в очередь не считается завершением генерации. После рестарта
пользователь открывает публикацию заново; старые transient-кнопки не начинают новую операцию.

## UC-PURCHASE-15 — Асинхронное уведомление о результате (план)

1. После будущего внедрения backend delivery contract закрыть чат, завершить тестовую оплату.
2. Проверить доставку результата после рестарта и обработку заблокированного бота.

**Ожидается:** durable уведомление восстанавливается без повторного grant; ошибка доставки
не меняет оплату/баланс. Сейчас push-уведомления не реализованы: доступна ручная проверка.
Статус остаётся **Не проверено**, зависимость — backend-owned delivery contract.
